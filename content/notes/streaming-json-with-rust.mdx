The premise of [pipe](https://github.com/avanaerschot/pipe) is simple: you have a large JSONL file and you want to transform it without loading it into RAM. `jq` does this badly by default (it buffers the whole thing). My tool streams it line by line.

Writing it taught me three things I didn't expect.

## 1. serde_json's Value is more useful than I thought

I expected to need a custom deserializer for everything. In practice, `serde_json::Value` plus a simple path syntax (`$.user.email`) covered 90% of use cases. The remaining 10% — things like renaming keys across nested arrays — required actual traversal code, but the built-in Value handles the basic get/set cases cleanly.

## 2. The real performance win is buffered I/O, not parallelism

My first instinct was to process lines in parallel using Rayon. This helped on CPU-bound transforms (regex substitution, base64 encode) but actually hurt on simple key-gets because the output ordering cost more than the parallelism saved. The much bigger win was using `BufReader` with a large buffer (1MB) instead of the default 8KB. On a 4GB file, this alone cut runtime by ~40%.

## 3. Error handling is the hard part

Rust's `?` operator makes the happy path clean. The painful part is deciding what to do with a malformed line: skip it, abort, or write it to a separate error file? I ended up adding `--on-error [skip|abort|sidecar]` and defaulting to `skip`. This took longer to design than the actual streaming logic.

---

The crate is published but small (31 stars at time of writing). I use it regularly for ETL prep — anything where I'd otherwise write a throwaway Python script to munge a log file before handing it to something else.
